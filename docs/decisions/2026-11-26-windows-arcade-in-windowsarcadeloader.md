# Windows arcade boards play in windowsarcadeloader, under a layer of each person's own

- **Decided:** Games from Windows-based arcade boards (Sega RingEdge, RingWide, ALLS and Europa-R, Taito Type X, Konami, Raw Thrills, Global VR, UNIS and more) play in windowsarcadeloader, built in CI at a pin with GE-Proton11-14 and winetricks 20260125 beside it in the image, never patched, started with no network like every emulator. What plays follows the loader's own lists, read in CI: a game it marks working plays, a gun game waits for a light gun, anything else is not supported. No save states and no RetroAchievements. Coins, Coin on Back, the cabinet's Service and Test switches on the stick clicks. The console's choices are one settings layer the loader reads last, the same for every game but for the picture options a game's own profile offers, which the console's picture level sets; a game whose profile offers none has no Picture row in its pause menu. CabinetOS supplies nothing that changes a game's own files: the library owner's script only adds the game's `.windowsloader` file. A game's folder on the drive and the console's one Windows setup are never written: each person's game runs under a layer of their own over both, and what the game wrote there is their save, sent to RomM as one zip of its folders under the loader's own name. The game's own registry keys travel in that save, as one file among Wine's user folders, and are laid over the shared setup's registry before each start; the rest of what Wine writes into the person's layer over the setup is emptied before each start.
- **Date:** 2026-11-26 (the plan, MMagTech, #762); the layers, the registry keys and the Picture row, 2026-11-27 in the build; nothing that changes a game's own files, MMagTech, 2026-11-27.
- **Why:** The loader holds each game's knowledge itself, as MAME does, so the console keeps one rule for every game; that is what was missing when PC-based arcade was closed. The trial of 2026-11-26 ran 13 games on ten boards at 4K on the reference console: 12 started, every stop was clean in under 0.7 s, and none reached the internet. Games write in three places, their own folder, their run folder in the Windows setup and Wine's user folders, and two people share the game's folder and the setup, so each write goes to a layer in the person's save folder. The game's folder is layered with fuse-overlayfs, because a games drive can be exFAT, which the kernel's own layering refuses; the Windows setup, always on the console's own drive, with the kernel's. Wine's server and services belong to no one process group, so the sandbox is a process space of its own, which a pause and a kill reach whole. The loader exits 0 however a game ended, and an arcade game has no quit, so an end nobody asked for is a failed start in the first minute and a crash after it. A game that keeps its screen size in the registry drew in a quarter of the screen at nearly every start without its keys (21 of 22 pictures on the reference console, 2026-11-27) and full screen with them (6 of 6); the rest of Wine's registry is the setup's, and an older copy of it would stand over a newer setup for good. A level that changes nothing would be a row that does nothing, and eight games at the pin offer a picture option. A game is the library owner's copy: the loader's notes say how to change one where it must be changed, and that is between the owner and the loader.
